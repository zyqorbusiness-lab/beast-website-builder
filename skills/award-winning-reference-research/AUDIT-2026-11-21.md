# Audit report: award-refs verify/collect hardening, second pass (21 Nov 2026)

Scope: the five gaps Sujon found in his independent review of commit `ace602a`
(WhatsApp, 21 Nov 2026 07:53 IST). One consolidated pass; his independent
re-check of this round is still pending, so nothing here is "final verified"
until he says so.

## What changed, point by point

### 1. `verify` rejected invalid input only after the request had already gone out

Before: the CLI called `fetchText` (with `redirect: 'follow'`) first and
validated the final URL after the fetch - the request, and every redirect hop
in between, had already been dispatched.

Now: `fetchGuarded()` validates the initial URL **before any request** and
follows redirects manually (`redirect: 'manual'`), validating **every redirect
target before the request to it is dispatched**. A rejected target is never
fetched: the result is `redirect-rejected` with the blocked target named.
Evidence: `tests/award-refs.test.mjs` (`fetchGuarded never dispatches a request
for an invalid initial URL`, `...off-domain redirect target without dispatching
it`, `...non-/sites/ awwwards.com page`, `...follows a valid same-source
redirect`, `...stops redirect loops`) and `tests/award-refs-cli.test.mjs`
(`CLI verify rejects an invalid URL before any network dispatch`, `CLI verify
never dispatches a rejected off-domain redirect target`), plus two
child-process tests that run the real `node award-refs.mjs` binary with a
logged mock fetch and assert from the dispatch log that **no request was made**
for an invalid URL and that a rejected redirect target was never requested
(`real CLI process: invalid verify input exits 2 and dispatches nothing`,
`real CLI process: an off-domain redirect target is never dispatched`).

### 2. `collect` never checked the final URL of a source fetch

Before: a redirected listing/feed response was parsed as if it were the
source's own data.

Now: every collect source has its own expected host + path validator
(`validateAwwwardsListingUrl`, `validateFwaFeedUrl`, `validateCssdaListingUrl`),
applied to the initial URL and every redirect hop through the same
`fetchGuarded`. A redirect away from the source's host/path is a structured
`redirect-rejected` source failure with the target named; the content is never
parsed. Evidence: `collect source validators pin each source to its own host
and path`, `CLI collect: a source redirect away from its host/path is a
structured failure, never parsed`.

### 3. Award-title match not end-anchored; jury corroboration too loose

Before: `/-\s*Awwwards\s+SOTD\b/` matched anywhere in the title, so
`X - Awwwards SOTD archive` read as the Site of the Day mark; and any numeric
`box-score__note` or any `grid-score` axis anywhere on the page corroborated.

Now: the mark must be an exact, end-anchored title suffix - `<name> - Awwwards
SOTD|SOTM|SOTY` with nothing after it. Jury corroboration is scoped to the
award's own jury structures (grounded in the live `/sites/` markup re-read on
21 Nov 2026): the overall score must come from inside the `class="box-score"`
jury box and be a valid 0-10 number, and axes must come from the
`grid-score--titles` row inside the `id="jury_votes"` section and be the
recognised jury axes (Design / Usability / Creativity / Content / Overall).
Orphan scores, look-alike grids and impossible scores do not corroborate.
Evidence: `parseAwwwardsSite requires an exact end-anchored title suffix`,
`parseAwwwardsSite does not corroborate from unrelated scores or axes`,
`parseAwwwardsSite ignores "Site of the Day" text outside the title evidence`
(updated: orphan `box-score__note` no longer counts), and the
`evaluateVerification` chain tests including the suffix-trap page.

### 4. `--pages 0` / negative / invalid values were not validated

Before: `--pages 0` skipped the fetch loop and reported the Awwwards source as
`ok` with zero entries, exiting 0.

Now: `--pages` must match `^[1-9]\d*$`, `--source` must be one of
`all|awwwards|fwa|cssda`, `--delay` a non-negative number. Any violation exits
2 with an error message before any network work. Evidence: `CLI collect
validates --pages and --source before any network dispatch (exit 2)` (five
invalid-input variants, each asserting zero dispatched requests) and
`real CLI process: collect --pages 0 exits 2 and dispatches nothing`.

### 5. Tests covered only pure helpers, not the real CLI behaviour

Before: tests exercised the parsers and the pure evaluator; actual CLI network
dispatch, the written `award-refs.json` / `REFERENCES.md`, counts and process
exit codes were untested.

Now: `tests/award-refs-cli.test.mjs` runs the real CLI path (`runCli`) with an
injected recording fetch, plus the real `node award-refs.mjs` process via the
`AWARD_REFS_TEST_FETCH_MODULE` test hook (`tests/fixtures/award-refs-test-fetch.mjs`)
with a per-URL dispatch log. Covered end to end: invalid input (exit 2, zero
dispatches), rejected redirect (exit 1, target never dispatched), verified
winner (exit 0), inconclusive (exit 1), HTTP/network failure (exit 1,
structured), `collect` written JSON + Markdown + counts + listing-candidate
labels, parse-empty (exit 1), and per-source failure statuses in the written
output. Aggregate `collect` behaviour is now defined and tested: exit 0 when at
least one requested source is `ok` (partial failure stays visible per source),
exit 1 when every requested source failed, exit 2 for invalid options.

## Honest limits (unchanged unless noted)

- This verifies award metadata from the gallery's own page (mark, jury scores,
  live URL, check date). It says nothing about design quality; the visual
  teardown stays a separate per-site step (`award-site-teardown-method`).
- Automated per-site `verify` covers Awwwards only. FWA and CSSDA individual
  verification is manual/browser work; CSSDA returned HTTP 502 to scripts on
  21 Nov 2026.
- Jury-evidence scoping is tied to Awwwards' current markup
  (`class="box-score"`, `id="jury_votes"`). If Awwwards changes that markup,
  corroboration fails closed (inconclusive), never open.
- The redirect guard validates http(s) redirects hop by hop; a page could still
  change content after load via JS, which is out of scope for a fetch-based
  check (browser verification covers that).
